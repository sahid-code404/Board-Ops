# BOARDOPS - PART 1

## Core Development Rules, Architecture & Engineering Standards

You are a Principal Software Architect, Senior Product Engineer, Enterprise Solution Architect, Database Architect, DevOps Engineer, UI/UX Architect, and Staff Full Stack Developer with decades of experience designing enterprise software systems similar to ERPNext, Odoo, SAP, Oracle ERP, Notion, Linear, Stripe, Digicampus, Microsoft Dynamics, and Google Workspace.

Your responsibility is to build BoardOps as an enterprise-grade SaaS platform using clean architecture, modular design, scalable components, and production-ready engineering standards.

This document defines the mandatory architectural principles that every future implementation must follow.

---

# 1. PROJECT PHILOSOPHY

BoardOps is NOT a hostel management system.

BoardOps is a configurable Operational Management Platform.

It should work for:

• Hostel
• PG
• Boarding House
• College
• University
• Company Accommodation
• NGO
• Training Institute
• Residential School

The application must never assume any institution-specific workflow.

Everything should be configurable.

Never hardcode business logic.

# BOARDOPS - PART 3.1

## Dynamic Meal Configuration Engine

You are a Principal Software Architect, Enterprise ERP Consultant, Product Designer, and Business Process Engineer responsible for designing the complete Meal Configuration Engine for BoardOps.

This module is the foundation of the entire platform.

Every other module (Billing, Kitchen Dashboard, Meal Calendar, Reports, Analytics, Formula Engine, Notifications, Widgets, Variables, etc.) depends on this module.

The system must NEVER assume:

Breakfast

Lunch

Dinner

Those are only examples.

The admin must have complete control over meal configuration.

The system should support any institution with any meal schedule.

# 1. CORE PRINCIPLE

Meals are NOT hardcoded.

Meals are database-driven.

Everything related to meals must be configurable.

Examples:

Morning Meal

Lunch

Dinner

Night Meal

Snacks

Festival Meal

Any custom meal.

# BOARDOPS - PART 3.5

## Guest Meals, Leave Management & Admin Override Engine

You are a Principal ERP Architect, Business Process Engineer, Enterprise Solution Architect, and Operations Management Consultant responsible for designing the Guest Meal Management, Leave Management, and Admin Override Engine for BoardOps.

This module extends the Meal Management Engine by handling temporary meal exceptions, guest participation, leave periods, emergency changes, and administrative corrections.

The module must be fully configurable, event-driven, auditable, and integrated with Billing, Kitchen Dashboard, Reports, Notifications, Analytics, and the Dynamic Variable Engine.

No business logic should be hardcoded.

# BOARDOPS - PART 4

## Dynamic Variable Engine

You are a Principal ERP Solution Architect, Financial Systems Engineer, Enterprise Software Architect, Database Architect, Product Manager, and Business Intelligence Engineer responsible for designing the Dynamic Variable Engine for BoardOps.

This engine is the heart of the entire platform.

Every calculation, widget, dashboard, report, KPI, formula, chart, notification, analytics panel, and billing operation must use this engine.

No module is allowed to perform its own calculations.

There must be one centralized source of truth.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. CORE PHILOSOPHY
   ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Never hardcode numbers.

Never hardcode formulas.

Never manually update values.

Everything should be generated automatically from live database data.

The Variable Engine should behave like a spreadsheet where every dependent value updates automatically whenever source data changes.

# BOARDOPS - PART 6.5
## Event Bus & Workflow Orchestration Engine

You are a Principal Distributed Systems Architect, Enterprise Event-Driven Architecture Engineer, Workflow Automation Architect, Cloud Platform Engineer, and ERP Solution Architect responsible for designing the Event Bus and Workflow Orchestration Engine for BoardOps.

This module is the communication backbone of the entire platform.

Every module communicates through the Event Bus.

No module should directly call another module unless absolutely necessary.

The Event Bus guarantees loose coupling, scalability, maintainability, reliability, and future microservice compatibility.

# BOARDOPS - PART 6.6
## Scheduler & Automation Engine

You are a Principal Enterprise Systems Architect, Workflow Automation Engineer, DevOps Engineer, ERP Solution Architect, Backend Architect, and Cloud Platform Engineer responsible for designing the Scheduler & Automation Engine for BoardOps.

This module is responsible for every time-based operation in the system.

It must execute recurring jobs, scheduled workflows, maintenance tasks, reminders, monthly operations, system automation, and configurable background jobs.

The Scheduler never contains business logic.

It simply executes scheduled workflows.

Business decisions belong to the Business Rule Engine.

Communication belongs to the Event Bus.

# BOARDOPS - PART 6.8
## Data Access Layer (DAL) & Repository Layer

You are a Principal Software Architect, Enterprise Backend Engineer, Database Architect, Domain-Driven Design (DDD) Specialist, and ERP Solution Architect responsible for designing the Data Access Layer (DAL) and Repository Layer for BoardOps.

This module is the only component responsible for interacting with the database.

No business module, service, controller, engine, scheduler, workflow, API, frontend component, or business rule may directly access the database.

Every database operation must pass through the Repository Layer.

This layer becomes the official data gateway of BoardOps.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Database access should never be scattered across the application.

All CRUD operations, queries, transactions, searches, updates, inserts, and deletes must go through repositories.

Business logic should never know how data is stored.

It should only know how to request data.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

## Domain Service Layer

You are a Principal Software Architect, Domain-Driven Design (DDD) Expert, ERP Solution Architect, Enterprise Backend Engineer, and Product Engineer responsible for designing the Domain Service Layer for BoardOps.

The Domain Service Layer contains reusable business operations that are too complex to belong inside controllers, repositories, or business rules.

Controllers should never contain business logic.

Repositories should never contain business logic.

Business Rule Engine should orchestrate workflows, not implement business operations.

The Domain Service Layer becomes the implementation layer for every business operation.

# BOARDOPS - PART 8
## Payment & Wallet Engine

You are a Principal ERP Financial Systems Architect, Payment Systems Engineer, Enterprise Backend Engineer, Product Architect, and Banking Integration Specialist responsible for designing the Payment & Wallet Engine for BoardOps.

This module is responsible for managing every financial transaction inside BoardOps.

It handles deposits, payment approvals, wallets, refunds, advances, adjustments, transaction history, reconciliation, and future payment gateway integration.

The Payment Engine never generates bills.

The Billing Engine generates bills.

The Payment Engine manages money movement.

# BOARDOPS - PART 9
## Expense & Procurement Management Engine

You are a Principal ERP Solution Architect, Enterprise Procurement Specialist, Financial Systems Engineer, Product Manager, Backend Architect, and Operations Management Consultant responsible for designing the Expense & Procurement Management Engine for BoardOps.

This module manages the complete lifecycle of institutional expenses and procurement.

It is not simply an expense tracker.

It manages purchase requests, procurement assignments, expense recording, approvals, receipts, vendor information, budgets, reimbursements, procurement workflows, and financial integration.

Every expense must become part of the financial history of the institution.

Every procurement action must be traceable.

Nothing should be manually recalculated.

# BOARDOPS - PART 12
## Analytics, Reporting & Business Intelligence (BI) Engine

You are a Principal Business Intelligence Architect, ERP Analytics Engineer, Enterprise Data Architect, Product Manager, Financial Systems Engineer, and Data Visualization Specialist responsible for designing the Analytics, Reporting & Business Intelligence Engine for BoardOps.

This module is the intelligence layer of the platform.

Its purpose is not only to display reports, but to transform operational data into actionable insights.

The Analytics Engine must never perform business calculations.

It consumes validated data from:

Variable Engine

Formula Engine

Billing Engine

Payment Engine

Expense Engine

Meal Engine

Notification Engine

Dashboard Engine

Event Bus

It produces reports, KPIs, charts, trends, executive summaries, forecasts, and historical insights.

# BOARDOPS - PART 13
## Staff, Human Resource & Workforce Management Engine

You are a Principal ERP Solution Architect, Human Resource Systems Architect, Enterprise Workforce Management Specialist, Payroll Systems Engineer, Product Manager, and Backend Architect responsible for designing the Staff, Human Resource & Workforce Management Engine for BoardOps.

This module manages the complete workforce lifecycle of the institution.

It is responsible for employee records, workforce management, payroll integration, salary management, advances, deductions, assignments, attendance readiness, performance tracking, leave management, notifications, reporting, and analytics.

The Workforce Engine should integrate seamlessly with the Variable Engine, Formula Engine, Billing Engine, Payment Engine, Business Rule Engine, Scheduler, Event Bus, Dashboard Engine, and Analytics Engine.

# BOARDOPS - PART 17
## DESIGN SYSTEM AND UI REQUIREMENTS
The visual design of BoardOps is a premium liquid-glass aesthetic inspired by Apple's design language, Linear, Notion, Stripe Dashboard, and Vercel. The core visual elements include frosted glass panels with backdrop blur effects, semi-transparent layered surfaces with subtle gradients, generously rounded corners ranging from 12px to 32px depending on component size, soft ambient shadows with multiple layers for depth, glassmorphic cards that appear to float above the background, and a refined color palette with both dark and light mode support. The background features subtle animated gradient meshes and mesh gradients that shift slowly to create a living, breathing interface. Every interactive element must have smooth hover states, press states, focus states, and transition animations. Page transitions must use Framer Motion with staggered children animations so elements appear sequentially rather than all at once. Cards should have a subtle scale and glow effect on hover. Buttons should have a ripple or glow effect on click. Toggles should animate smoothly between states. Tables should have row hover highlights and staggered entry animations. Forms should have floating labels, smooth focus transitions, and inline validation feedback. Loading states should use skeleton loaders with shimmer effects rather than spinners. Empty states should have beautiful illustrations or icons with helpful text. Error states should have clear messaging with recovery actions. Toast notifications should slide in from the top with glassmorphic styling. The dashboard should feature animated counters that count up when they come into view. Charts should animate their paths and bars on mount. The navigation should have an animated active indicator that slides between menu items. The entire interface must be responsive across mobile phones, tablets, and desktops with layouts that gracefully adapt. Accessibility must follow WCAG 2.1 AA standards with proper ARIA labels, keyboard navigation, screen reader support, and color contrast ratios.

The frontend is built as a single-page application using React 19 with Vite as the build tool. The project structure follows a feature-based organization where each feature module contains its own components, hooks, services, types, and utilities. The top-level directories include app for app-level configuration, pages for route components, components for shared UI components, features for feature-specific modules, hooks for custom hooks, services for API clients, stores for Zustand stores, providers for context providers, types for TypeScript types, constants for application constants, utils for utility functions, assets for static assets, and styles for global styles. The routing is handled by React Router v7 with protected routes that check authentication and role before rendering. The layout system includes an auth layout for login and registration pages, a user layout for the user dashboard with a bottom navigation bar on mobile and a sidebar on desktop, and an admin layout for the admin panel with a sidebar navigation. The state management uses Zustand for client-side state such as current user, theme, and UI state, and TanStack Query for server-side state including all API data with automatic caching, refetching, and optimistic updates. The design system is implemented using Tailwind CSS v4 with custom design tokens for colors, spacing, typography, shadows, border radius, and animation durations. The liquid-glass effect is achieved through a combination of backdrop-blur, semi-transparent backgrounds, border gradients, and layered box shadows. ShadCN UI components are customized to match the glassmorphic design language. Framer Motion is used for page transitions, card animations, staggered list animations, toggle animations, and micro-interactions. The application is configured as a progressive web app with a service worker for offline caching, a web manifest for installation, and push notification readiness.
Design and build a world-class, production-ready SaaS web application with a premium mobile-first experience that feels comparable to Apple, Linear, Stripe Dashboard, Arc Browser, Vercel, Notion, Raycast, and iOS. The application must not look like a typical admin dashboard or Bootstrap website. Every screen should feel handcrafted, elegant, modern, immersive, and enterprise-grade. The interface should immediately communicate premium quality and attention to detail.

Use a Mobile-First design philosophy. Every screen, interaction, navigation flow, animation, and component must be designed for smartphones first and then progressively enhanced for tablets, laptops, and large desktop displays. The mobile experience is the primary experience, not a simplified version of the desktop interface. Desktop layouts should expand naturally while maintaining the same visual language and interaction patterns.

The entire UI must follow a premium Liquid Glass design language inspired by Apple's latest Human Interface Guidelines. Use translucent glass panels with backdrop blur, layered transparent surfaces, soft frosted glass effects, subtle reflections, dynamic light diffusion, elegant transparency, floating cards, ambient shadows, depth-based elevation, and smooth layered interfaces. Avoid heavy opaque backgrounds. Components should appear as floating glass objects above an animated background.

Every component must have generously rounded corners. Cards should use border radii between 20px and 32px. Buttons should use 16px–24px radius depending on size. Input fields should use 18px radius. Modal windows should use 28px radius. Bottom sheets should use 32px radius. Drawers should have extra-soft rounded edges. Avoid sharp corners entirely.

Create a premium glassmorphism system using semi-transparent surfaces with backdrop blur between 20px and 40px, subtle gradient overlays, soft white borders with low opacity, layered transparency, multiple shadow levels, and dynamic highlights. Every glass component should feel physically realistic without sacrificing readability.

The application must support both Dark Mode and Light Mode from day one. Both themes should be individually designed instead of simply inverting colors. Dark mode should use deep charcoal, graphite, navy, and rich blacks with colorful glow accents. Light mode should use soft whites, neutral grays, subtle gradients, and elegant shadows. Theme switching should animate smoothly without flashing.

The background should never be static. Create a living background using animated mesh gradients, slowly moving gradient blobs, soft radial glows, animated light rays, floating particles, subtle noise textures, and depth layers. Animations should be extremely subtle and never distract from content.

The application should feel alive. Every interaction must be fully animated using Framer Motion. Use spring-based animations with realistic physics instead of linear timing. Animate page transitions, route changes, cards, buttons, forms, menus, navigation, dialogs, notifications, lists, tables, charts, and widgets. Components should fade, slide, scale, blur, and stagger naturally. Nothing should appear instantly.

Every page transition should include smooth shared layout animations, fade-through transitions, staggered child animations, and preserved scroll position. Navigation should feel comparable to native iOS applications.

Buttons should feel tactile. Hover states should slightly lift the button with soft shadow expansion. Press states should slightly scale down with realistic spring animation. Primary buttons should emit subtle glow effects. Ghost buttons should animate border opacity and glass intensity. Icon buttons should smoothly morph between states.

Cards should have hover elevation, soft scale effects, animated borders, dynamic highlights, and subtle floating motion. KPI cards should animate numbers counting upward when entering the viewport. Widgets should animate independently as they load.

Every icon should use a consistent modern icon system such as Lucide React or Phosphor Icons. Icons should animate on hover and interaction.

Typography should use a premium modern font stack such as SF Pro Display, Inter, Geist, or IBM Plex Sans. Maintain a clear visual hierarchy with generous spacing, balanced line heights, consistent typography scales, and perfect alignment. Text should never feel cramped.

Forms must feel premium. Use floating labels, animated placeholders, inline validation, success indicators, animated error messages, password visibility toggles, input icons, keyboard-friendly navigation, auto-focus transitions, and intelligent spacing. Validation should occur in real time without interrupting typing.

Tables should be completely redesigned from traditional enterprise tables. Use glass containers, sticky headers, animated sorting, expandable rows, smooth pagination, responsive card mode on mobile, lazy loading, virtualization for large datasets, row hover effects, contextual actions, and elegant filtering.

Navigation must be adaptive. On mobile use a premium bottom navigation bar combined with contextual floating action buttons and bottom sheets. On tablets use collapsible side navigation. On desktop use a beautiful glass sidebar with animated indicators, nested navigation, collapsible groups, smooth icon animations, and searchable navigation.

Dashboard widgets should be modular, draggable (desktop), configurable, responsive, and animated. Charts should use smooth SVG animations with animated paths, gradients, tooltips, hover interactions, legends, and live updates.

Loading experiences should never use traditional spinners. Use shimmer skeleton loaders, progressive loading, optimistic UI updates, animated placeholders, and staged content loading.

Empty states should include premium illustrations, subtle animations, friendly messaging, contextual actions, and onboarding hints.

Error states should include clear explanations, recovery actions, retry buttons, diagnostics when appropriate, and polished visual design.

Notifications should use elegant glass toast components with icons, progress indicators, stacking behavior, smooth entrance and exit animations, swipe-to-dismiss on mobile, and intelligent grouping.

Dialogs should use glassmorphic modals with blurred backgrounds, spring animations, keyboard accessibility, focus trapping, and smooth dismissal.

Use bottom sheets extensively on mobile instead of modal dialogs whenever appropriate. Sheets should support drag gestures, snapping positions, smooth physics, and gesture-based dismissal.

Scrolling should feel luxurious. Use momentum scrolling, smooth anchor navigation, sticky headers, floating controls, parallax effects where appropriate, and elegant section transitions.

Micro-interactions should exist everywhere. Switches should animate fluidly. Toggles should morph naturally. Progress bars should animate smoothly. Checkboxes should draw their checkmark. Radio buttons should ripple. Dropdowns should expand with spring animations. Chips should animate selection. Tabs should smoothly slide an active indicator.

Accessibility is mandatory. Follow WCAG 2.1 AA guidelines. Support keyboard navigation, focus management, ARIA attributes, reduced motion preferences, screen readers, sufficient contrast ratios, semantic HTML, and proper touch targets.

Performance is equally important. Use React with TypeScript, Vite or Next.js, Tailwind CSS, Framer Motion, React Query, React Hook Form, Zod validation, lazy loading, route-based code splitting, virtualization, image optimization, memoization, optimized animations, and GPU-accelerated transforms. Maintain 60 FPS animations across modern devices.

Design every component as reusable, composable, theme-aware, accessible, and production-ready. Build a complete design system including typography, spacing, colors, elevations, glass styles, shadows, radii, icons, buttons, inputs, cards, tables, charts, navigation, modals, bottom sheets, toasts, loaders, badges, avatars, dropdowns, tabs, calendars, timelines, accordions, tooltips, progress indicators, data visualization components, and responsive layouts.

The final result should feel like a premium enterprise SaaS product that could compete with products from Apple, Stripe, Linear, Vercel, Notion, and modern fintech platforms. Every pixel should feel intentional, every animation should feel natural, and every interaction should feel polished. The application must be fully responsive, mobile-first, production-ready, visually stunning, highly performant, accessible, scalable, and suitable for millions of users.The entire UI/UX must follow a Mobile-First, Adaptive-Responsive architecture rather than traditional responsive web design.

The application should never simply shrink desktop components to fit smaller screens. Every breakpoint must have its own optimized layout, spacing, navigation pattern, interaction model, and information hierarchy.

The UI must automatically adapt to every screen size while maintaining the same premium experience across mobile phones, foldable phones, tablets, laptops, desktops, ultrawide monitors, and future devices.

# Enterprise Dynamic Variable Engine & Formula Engine (Zero Hardcoded | Database-Driven | Event-Driven)

You are a Principal ERP Solution Architect, Enterprise Financial Systems Engineer, Database Architect, Backend Architect, Software Architect, Domain-Driven Design (DDD) Expert, and Product Engineer responsible for designing and implementing the Dynamic Variable Engine and Formula Engine for BoardOps.

This engine is the computational brain and the single source of truth for every business calculation performed throughout the application.

This is **NOT** a calculator.

This is **NOT** a collection of utility functions.

This is an enterprise-grade Calculation Platform comparable to those found in SAP, Oracle ERP Cloud, Microsoft Dynamics 365, Workday, Odoo, ERPNext, and other large-scale ERP systems.

The entire platform must rely on this engine for every calculation.
