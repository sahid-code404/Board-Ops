BoardOps Product Requirements Document (PRD)
PART 1 — Project Foundation
1. Product Overview
Product Name

BoardOps

Tagline

The complete operations platform for institutional mess management.

Product Vision

BoardOps is a centralized web application that digitizes and automates the complete operational workflow of an institution's mess, from resident onboarding and meal booking to billing, payment verification, expenses, fund tracking, notifications, and administration.

Instead of managing operations through registers, spreadsheets, WhatsApp groups, and manual calculations, BoardOps provides one integrated platform where every activity is tracked, validated, and auditable.

The system is designed to reduce manual work, eliminate calculation errors, improve transparency, and provide real-time visibility into mess operations for both residents and administrators.

2. Problem Statement

Many institutional messes currently face issues such as:

Manual attendance of meals.
Paper-based registrations.
Manual bill calculations.
Payment verification through chat screenshots.
No centralized expense tracking.
No live fund visibility.
No meal analytics.
No approval workflow.
No audit history.
Poor communication between residents and administrators.

BoardOps solves these issues with structured workflows and centralized management.

10. Core Terminology

To avoid ambiguity throughout the PRD:

Resident: An approved institution member who uses the mess.
Administrator: A user responsible for managing mess operations.
Meal: A configurable food service (e.g., Morning Meal, Dinner).
Booking: A resident's decision to enable or disable a meal for a specific date.
Meal Configuration: The definition and rules governing a meal (service time, cutoff, icon, etc.).
Bill: A financial record generated for a resident for a billing period.
Deposit: Money submitted by a resident toward their account.
Payment Proof: Evidence uploaded by a resident to support a deposit.
Expense: A recorded operational cost of running the mess.
Fund: The financial balance derived from deposits and expenses.
Variable: A configurable system value used in calculations or behavior (e.g., room rent, cleaning charge).
Notification: A message delivered by the system to inform users about events or actions.
Archive: A state where a record is retained but hidden from normal operations.
Deletion Queue: A temporary holding area for soft-deleted records before permanent removal.
KPI (Key Performance Indicator): A summarized metric displayed to provide quick operational insight (e.g., Active Users, Total Deposits).

2. Formula Engine

Every financial calculation shall be configurable using variables.

Administrators define formulas by selecting variable slugs instead of fixed values.

Example:

meal_charge =
(

-

The system must validate formulas before saving them and prevent invalid or circular references.

3. Formula Builder (Instead of Typing)

Rather than requiring administrators to type formulas manually, the interface should provide a visual formula builder that allows them to:

Select variables from a searchable list.
Insert operators (+, −, ×, ÷, parentheses).
Preview the generated expression.
Validate the formula before saving.
Test the formula with sample values.

Advanced users may switch to a text editor for direct editing.

4. Meal Charge Calculation

Meal charge is not stored manually.

It is automatically calculated based on the configured formula.

Default example:

Meal Charge =
(Total Expense - Total Guest Meal Revenue)
÷
Total Resident Meals

Administrators may replace this formula with another valid one if their institution follows a different billing policy.

5. Monthly Billing Cycle

Billing is generated automatically.

Default workflow:

Month Ends

↓

System freezes previous month's meal data

↓

Formula Engine calculates meal charge

↓

Resident bills are generated

↓

Bills become available on the 2nd day of the next month

↓

Residents receive notification

↓

Residents can submit payment

Administrators may regenerate bills only before the billing cycle is finalized. Any regeneration must be logged.

6. Locked Meals & Admin Override

Meal bookings become locked after the configured cutoff time.

Residents cannot modify locked meals.

Administrators may override a locked meal for an individual resident when necessary.

Each override records:

Original value
New value
Administrator
Date and time
Mandatory reason

In the resident interface, overridden meals display a visual indicator (e.g., an "Admin Override" badge or icon).

Residents submit:

Payment amount

Optional note

PRD Addendum 2 — Resident Fund Policy & Meal Restriction Engine
8. Resident Wallet Model

BoardOps uses a running balance model instead of bill-by-bill payments.

Wallet Principles

Residents may deposit money at any time.

Every approved deposit immediately increases the resident's available balance.

At the end of each billing cycle, generated bills are automatically deducted from the resident's available balance.

If the wallet balance exceeds the bill amount, the remaining balance is carried forward to the next billing cycle.

If the wallet balance is insufficient, the remaining unpaid amount becomes the resident's outstanding due.

The resident always has visibility into:

Current wallet balance
Outstanding due
Total deposits
Total deductions
Available balance after pending bills
9. Balance Monitoring Engine

The system continuously evaluates every resident's financial status.

The engine compares:

Available Wallet Balance

vs

Required Minimum Balance

The required minimum balance is calculated using configurable formulas and system variables.

Example:

Required Minimum Balance =
Estimated Expense Per Head

or

Required Minimum Balance =
Current Meal Charge × Estimated Meals Remaining

or any administrator-defined formula.

No values are hardcoded.

10. Low Balance Policy

When a resident's available balance falls below the required threshold:

Status changes to:

Low Balance

The resident receives:

In-app notification
Dashboard warning
Optional email notification (if enabled)

The dashboard displays:

"Your available balance is below the required amount. Please deposit funds before the grace period expires to avoid automatic meal suspension."

11. Grace Period Engine

A configurable grace period begins immediately after the Low Balance status is triggered.

Example:

Grace Period = 2 Days

The number of grace days is fully configurable by administrators.

No fixed duration is embedded in the application.

During the grace period:

Residents can continue booking meals.
Existing meal bookings remain unchanged.
Deposits can still restore compliance.
Reminder notifications may be sent according to configured schedules.
12. Automatic Future Meal Suspension

If the resident still has insufficient balance after the grace period expires, the system automatically suspends future meal bookings.

Only future meals are affected.

Historical meals and already-consumed meals remain unchanged.

The system:

Turns OFF all future booked meals.
Prevents new meal bookings until compliance is restored.
Displays a suspension notice.
Records the action in the audit log.

The resident is informed that the suspension resulted from the Low Balance policy.

13. Automatic Restoration

When sufficient funds are approved:

The system automatically removes the financial restriction.

However, future meals that were automatically turned OFF are not automatically turned back ON.

Residents must review and re-book any meals they still wish to receive. This avoids accidental bookings after a long period of suspension.

14. Administrative Financial Override

Administrators may temporarily exempt individual residents from the Low Balance policy.

Possible reasons include:

Scholarship
Medical emergency
Administrative approval
Special institutional permission
Other documented reasons

Each override requires:

Resident
Administrator
Reason (mandatory)
Start date
End date (optional)
Supporting note (optional)

Every override is audit logged.

15. Low Balance Policy Configuration

Administrators can configure:

Enable/disable the policy.
Grace period duration.
Reminder schedule.
Formula used to determine the required minimum balance.
Notification templates.
Automatic meal suspension behavior.

Changes affect only future evaluations and do not retroactively modify previous decisions.

16. Financial Status Indicators

Each resident has one financial status:

Healthy — Balance meets or exceeds the required threshold.
Low Balance — Balance is below the threshold; grace period is active.
Restricted — Grace period has expired and future meal booking is suspended.
Exempted — Resident has an active administrative override.
Overdue — Outstanding dues remain after bill generation (informational status).

These statuses are visible to both the resident and administrators.

🚀 My Final Review of BoardOps

After everything we've designed, I would make five structural improvements before a single line of code is written.

1. Introduce a State Machine Framework (High Priority)

Almost every entity in BoardOps has lifecycle states:

Bill
Payment
Resident
Refund
Purchase
Expense
Restriction

Instead of implementing lifecycle rules separately, define a common state machine framework. Every transition (e.g., Pending → Approved) should validate permissions, business rules, trigger notifications, create timeline events, and write audit logs consistently.

2. Standardize a Business Event Catalog (High Priority)

Rather than modules talking directly to each other, define events such as:

PaymentApproved
BillPublished
ResidentRestricted
MonthlyClosingCompleted
RefundProcessed

Modules subscribe to events instead of tightly coupling their logic. This keeps the architecture modular and easier to extend.

3. Define a Configuration Registry (Medium Priority)

BoardOps already distinguishes:

Settings
Policies
Variables

Create a registry documenting every configurable item, including:

Default value
Allowed range
Validation
Effective date
Snapshot behavior

This prevents configuration drift as the system grows.

4. Add a Reference Number Service (Medium Priority)

Instead of every module generating identifiers independently, centralize generation for:

Bills
Payments
Purchases
Refunds
Adjustments

Using configurable formats and guaranteed uniqueness.

5. Add a Validation Engine (Medium Priority)

Many modules share similar validation patterns:

Required fields
Permission checks
State transition validation
Date validation
Financial validation

A common validation layer ensures consistent behavior across the platform.
